# 仕様

## 機能の層

機能を4つの層に分けて決める。このリポジトリが扱うのは (1)〜(3)。

| 層 | 内容 | 状態 |
|---|---|---|
| (1) OIDC の RP としての機能 | プロトコルとしての振る舞い | 確定 |
| (2) AVideo との統合 | ユーザの作成と突き合わせ、claim から権限への対応、ネイティブログインの制御 | 確定 |
| (3) IdP 固有の拡張 | Keycloak Admin API による定期同期（任意機能） | 確定 |
| (4) 利用者側の設定値 | role 名、IdP の URL など | このリポジトリでは扱わない |

**特定の環境の値（ホスト名、realm 名など）はリポジトリに入れない。** すべて設定で受け取る。

## (1) OIDC の RP としての機能

### 基本

| 機能 | 対応 | 備考 |
|---|---|---|
| Discovery（`.well-known/openid-configuration`） | 対応 | 設定は issuer の URL だけで済むようにする |
| Authorization Code Flow | 対応 | 唯一の対象フロー |
| PKCE（S256） | 対応 | |
| `state` / `nonce` の検証 | 対応 | |
| ID Token の検証 | 対応 | 署名、`iss` / `aud` / `exp` / `iat` / `nonce` |
| JWKS の取得とキャッシュ | 対応 | `kid` が見つからなければ取り直す（鍵のローテーションに追従するため） |
| UserInfo エンドポイント | 対応（任意） | ID Token に必要な claim がない IdP 向け |
| scope の指定 | 対応 | 既定は `openid profile email` |
| Implicit / Hybrid Flow | 対象外 | 非推奨のため |
| Refresh Token | 対象外 | ログイン後は AVideo のセッションで動くため、トークンを持ち続ける必要がない |

### クライアント認証

トークンエンドポイントで、プラグイン自身が IdP に身元を示す方式。

| 方式 | 対応 |
|---|---|
| `client_secret_basic` | v1 |
| `client_secret_post` | v1 |
| `private_key_jwt` | v2 |

**方式は差し替えられる作りにする。** v2 で `private_key_jwt` を足すときに、他の部分に手を入れずに済むようにするため。

IdP が対応している方式は Discovery の `token_endpoint_auth_methods_supported` で分かる。対応していない方式は選べないようにする。

### ログアウトとセッション

| 機能 | 対応 | 備考 |
|---|---|---|
| RP-Initiated Logout | 対応 | AVideo でログアウトすると IdP 側もログアウトする |
| Back-Channel Logout | 対応 | IdP からの通知で AVideo のセッションを切る |
| Front-Channel Logout | 対象外 | ブラウザの第三者 Cookie 制限で動かないことが多い |
| Session Management（iframe） | 対象外 | 同上 |

### IdP の数

**扱う IdP は1つ。** 複数の IdP をまとめるのは IdP 側の役割（Keycloak の Identity Brokering など）と考える。SNS ログインは AVideo に既存のプラグインがある。

**ユーザの識別子は issuer と `sub` の組で保存する。** `sub` は IdP ごとに一意なだけなので、issuer の設定を誤って別の IdP に向けたときに、別人のアカウントに入れてしまう事故を防ぐ。

### 運用

| 機能 | 備考 |
|---|---|
| 時刻のずれの許容（clock skew） | 設定できるようにする |
| TLS 証明書の検証 | 無効にする設定は用意しない。独自の CA を使う場合のために、CA 証明書のパスだけ指定できるようにする |
| デバッグログ | トークンの中身はログに出さない |

### 実装方針

**RP の処理は自作し、JWT の署名検証と JWKS の処理だけ AVideo 本体同梱の `firebase/php-jwt` を使う。**

- OIDC クライアントライブラリを同梱すると、AVideo 本体の `vendor/` と同じ PHP プロセスで読み込まれ、依存の版が衝突するおそれがある
- AVideo 同梱の Hybridauth の Keycloak プロバイダは、Discovery・ID Token の検証・nonce・PKCE を持たないため使わない
- 署名の検証は自作しない

**プラグインが発行する SQL は、MariaDB と MySQL の両方で動く書き方にする。** AVideo 本体は MariaDB を主に想定しているが、MySQL で運用するサイトもあるため。どちらか専用の構文（`ADD COLUMN IF NOT EXISTS` など）は使わず、両方でテストする。

本体の `firebase/php-jwt` の版に依存するので、AVideo の更新時に動作を確認する（README の「動作確認済みの AVideo」）。

## (2) AVideo との統合

### ユーザの作成と突き合わせ

| 項目 | 仕様 |
|---|---|
| 突き合わせのキー | プラグイン専用のテーブルに `(issuer, sub) → users.id` を保存する。`(issuer, sub)` と `users_id` の両方に一意制約を付け、1対1にする |
| 紐付けがないとき | 新しいユーザを作る（JIT）。JIT は設定で無効にでき、その場合は事前に紐付けたユーザだけがログインできる |
| 既存の AVideo ユーザへの紐付け | **自動では紐付けない。** メールアドレスが同じでも紐付けない。管理者が手動で紐付ける手段を用意する |
| username | claim から作る（既定は `preferred_username`、設定で変えられる）。使えない文字を除き、45 文字に切り詰め、重複したら連番を付ける。**作成後は変えない** |
| ログインのたびに更新する属性 | 名前、メールアドレス、`emailVerified`（`email_verified` claim から）。属性ごとに更新するかを設定できる |
| パスワード | 推測できない長い乱数を入れ、誰にも知らせない（`users.password` が NOT NULL のため） |
| AVideo 側で無効のユーザ（`status = 'i'`） | IdP で認証が通っても、ログインを拒否する |
| 新規ユーザの既定の user group | 本体の設定（`userDefaultUserGroup`）に従う |

**本体の SNS ログインの仕組み（`User::createUserIfNotExists`）は使わない。** username が一致すれば既存のユーザとしてログインさせる作りで、IdP 側でメールアドレスや表示名を他人と同じにすると、他人のアカウントに入れてしまうため。

**username を変えないのは、** IdP 側で改名されても、チャンネルの URL などが変わらないようにするため。突き合わせは `sub` で行うので、username が IdP とずれても問題ない。

### claim から権限への対応

対象は AVideo のフラグ `isAdmin` / `canUpload` / `canStream` / `canViewChart` / `canCreateMeet`。

| 項目 | 仕様 |
|---|---|
| claim の指定 | ドット区切りのパスで指定する（例: `resource_access.avideo.roles`）。値は配列でも文字列でも受け付ける |
| 対応の書き方 | 「claim の値 → 付けるフラグ」の対応表を設定で持つ |
| 複数の値に該当したとき | 該当したフラグをすべて付ける（OR） |
| プラグインが管理するフラグ | 設定で選んだフラグだけを、ログインのたびに claim の内容で上書きする。選ばなかったフラグには触れない |
| claim がない、または値が空のとき | 空の一覧として扱う。管理対象のフラグはすべて 0 になる |
| claim をどこから読むか | ID Token と UserInfo を合わせて読む。Access Token は読まない |
| ログインに必要な条件 | 「この claim にこの値が含まれていなければログインを拒否する」という条件を任意で設定できる |

**管理するフラグを選べるようにするのは、** IdP を正とする部分と、AVideo の管理画面で個別に管理する部分を、サイトごとに分けられるようにするため。例えば、管理者は IdP で管理し、`canStream` は AVideo 側で個別に付ける、という運用ができる。

**Access Token を読まないのは、** Access Token はリソースサーバ向けのもので、クライアントが中身を解釈する前提のものではないため。IdP によっては、role を ID Token や UserInfo に入れる設定が必要になる。

### claim から user group への対応（任意機能）

user group は AVideo で動画の公開範囲に使う。仕組みはフラグと同じにする。

| 項目 | 仕様 |
|---|---|
| 対応の書き方 | 「claim の値 → AVideo の user group」の対応表を設定で持つ |
| user group の指定 | ID で持つ（AVideo 側で名前を変えても対応が壊れないように）。設定画面には名前も表示する |
| プラグインが管理する group | 設定で選んだ group だけを、ログインのたびに上書きする。選ばなかった group には触れない |
| 既定の group との関係 | 新規ユーザの既定の group（`userDefaultUserGroup`）が管理対象に含まれていれば、claim の内容で上書きされる |

### 未ログイン時の自動リダイレクト

| 項目 | 仕様 |
|---|---|
| 既定 | 無効。設定で有効にする |
| 対象 | 画面の表示（HTML）だけ。API、JSON、動画ファイル、Encoder 向けの通信はリダイレクトしない |
| 戻り先 | ログイン後は元のページに戻す |
| 例外 | ネイティブログインの画面には到達できるようにする（break-glass のため） |

### ネイティブログインの制御

**本体の `disableNativeSignIn`（CustomizeUser）は、画面からログインフォームを消すだけ。** ログインの API（`objects/login.json.php`）は、ユーザ名とパスワードを送れば受け付ける。制限するには、プラグインがサーバ側で拒否する必要がある。

| 項目 | 仕様 |
|---|---|
| 制御モード | 「制限しない / IdP に紐付いたユーザだけ禁止する / 許可リストのユーザだけ許可する」から選ぶ |
| 制御の方法 | `onUserSignIn` で判定し、許可されていなければ即座にログアウトさせ、記録を残す |

本体にはログインの前に割り込むフックがなく、使えるのはログイン成立の直後に呼ばれる `onUserSignIn` だけ。そのため「成立直後に取り消す」形になる。**ログインの API の応答がどう見えるかは、実装時に確認する。**

### Encoder からのログイン

AVideo の画面からアップロードすると、AVideo はログイン中のユーザの名前とパスワードのハッシュを Encoder に渡し、Encoder はそれを使って AVideo にログインする（`encodedPass`）。**投稿者のネイティブログインを禁止すると、アップロードが壊れる。**

| 項目 | 仕様 |
|---|---|
| Encoder の例外 | 送信元の IP が、設定した Encoder の IP であれば、ネイティブログインの制御を掛けない |

**Encoder 専用のアカウントを作る案は採らない。** 動画の所有者が投稿者ではなく、専用のアカウントになってしまうため。

### モバイルアプリ

**v1 では対象外。** IdP に紐付いたユーザは、モバイルアプリからはログインできない。

- 対応するには、アプリ向けの別のログインの流れが必要で、規模が大きい
- AVideo のモバイルアプリ（WWBN が提供）に、第三者のプラグインがログイン手段を追加できるかは未確認

v2 以降の候補とする。v1 でも、ユーザの作成・突き合わせ・権限の反映は Web のログインの流れから切り離した作りにしておき、別の入口から呼べるようにする。

## (3) IdP 固有の拡張

### Keycloak の同期

Keycloak Admin API を使い、IdP 側の変化を AVideo に反映する。v1 に含める。任意機能で、使わなければ (1) と (2) だけで動く。

#### 対象と反映する内容

| 項目 | 仕様 |
|---|---|
| 対象 | IdP に紐付いたユーザだけ。紐付いていないユーザと、ネイティブログインの許可リストのユーザには触れない |
| ユーザの作成 | しない。作成は初回ログイン時の JIT だけで行う |
| 削除された（API で 404） | AVideo 側で無効化する（`status = 'i'`）。物理削除はしない |
| 無効化された（`enabled = false`） | AVideo 側で無効化する |
| 再び有効化された | 同期が無効化したユーザだけ有効に戻す。管理者が手動で無効化したユーザは戻さない（誰が無効化したかを記録する） |
| role や group の変更 | ログイン時と同じ対応表で、管理対象のフラグと user group を再計算する |
| 名前やメールアドレスの変更 | ログイン時と同じ設定で更新する |
| 無効化したユーザのセッション | 即座に切る（Back-Channel Logout 用のセッションの対応表を使う） |

**プラグインの責任範囲はユーザの無効化まで。動画には触れない。** 動画の公開状態を変えると、元に戻すときに元の状態が分からなくなるため。無効化したユーザの動画の扱いは、管理者か他の仕組みに任せる。

#### role の読み方

ログイン時は claim のパスから読むが、Admin API が返すのは role の割り当てそのもの。そのため同期には、「どの client の client role を読むか（または realm role か、group か）」の設定が別に要る。

**ログイン時の設定と食い違うと、権限が食い違う。** 設定画面では両者を並べて表示する。

#### Admin API への認証

- 同期専用の client を作り、service account（client credentials）で認証する。ログイン用の client とは分ける
- 権限は `realm-management` の `view-users` / `query-users` だけにする
- **シークレットは AVideo の DB に保存しない。** 環境変数かファイルのパスで CLI に渡す

#### 実行

- `plugin/LoginOIDC/` 配下の CLI を cron から実行する。間隔は利用者が決める
- 同時に複数が走らないように排他制御する
- 変更内容だけを表示する dry-run を用意する
- 実行ごとに結果の要約（無効化の件数、権限変更の件数など）をログに出す

#### 安全装置

- **API の失敗（タイムアウト、5xx、認証エラー）では何も変更しない。** 無効化するのは 404 と `enabled = false` のときだけ
- **1回の実行で無効化する割合が閾値を超えたら、何も変更せずに止める。** 設定を誤って別の realm を向けたときなどに、全員を無効化する事故を防ぐ
